# beads-viewer-e2e

Behavioral Playwright test suite for `beads-viewer` (Go htmx server-side
viewer at `gardenio/controller/cmd/beads-viewer/`).

Sibling to `gardenio/tests/beads-viewer-screenshots/`:

|                | beads-viewer-screenshots | beads-viewer-e2e (here)         |
| -------------- | ------------------------ | ------------------------------- |
| Purpose        | Visual MR review         | Behavioral coverage + CI gate   |
| Asserts on     | Image bytes (advisory)   | DOM, htmx swaps, navigation     |
| Workers        | 1 (deterministic visual) | parallel                        |
| Auto-boots app | No                       | Yes (Playwright `webServer:`)   |

Plan of record: `gardenio/plans/beads-viewer-playwright-tests.md`.
Epic: `ka-0000004611`.

## Run

From the monorepo root:

```sh
make test-beads-viewer-e2e
```

That target installs deps, installs chromium, then runs the suite.
Playwright will auto-boot the viewer via the `webServer:` block in
`playwright.config.js`.

The viewer needs a beads daemon reachable at `BEADS_HTTP_ADDR`
(default `http://localhost:8080`). For local dev that means:

```sh
kubectl -n gardenio port-forward svc/gardenio-beads 8080:8080
```

**Do not run the suite against the production beads daemon.** The seed
step (Phase T2, see below) writes 7 labelled fixture beads + 1 type
config to whatever daemon `BEADS_HTTP_ADDR` points at. Use a hermetic
test daemon, or at minimum a development cluster you do not mind
polluting with `fixture:e2e:*`-labelled beads.

## Fixtures (Phase T2 — ka-0000006317)

**Strategy chosen:** seeded real daemon with label-based stable ids.
Matches the plan recommendation in
`gardenio/plans/beads-viewer-playwright-tests.md` ("seeded real daemon,
pinned bead ids, because the wire protocol IS part of what we're
testing"). No `gb decision` was raised — the choice follows the plan,
the alternative (in-process fake daemon) was explicitly rejected
because it risks divergence from the real wire protocol.

### How "pinned ids" works

Bead ids (`kd-` + nanoid) are auto-generated by the daemon and cannot
be supplied by the client, so "pin one bead per type" cannot mean
hard-coded ids. Instead:

1. Each canonical fixture is identified by a stable label
   `fixture:e2e:<key>` (e.g. `fixture:e2e:schedule`).
2. `seed/seed.mjs` upserts each fixture: if a bead with the label
   already exists, reuse it; otherwise create one.
3. The resolved label-to-id mapping is written to `fixtures/ids.json`
   (a generated file; gitignored).
4. Tests load the manifest via `loadFixtures()` from `tests/_helpers.js`
   and reference fixtures by key:

   ```js
   import { fixtureId } from './_helpers.js';
   await page.goto(`/${fixtureId('schedule')}`);
   ```

Re-running the seed against the same daemon is a no-op (same ids
returned). This is what makes ids "stable across runs".

### The 7 canonical fixtures

One bead per per-type partial in
`gardenio/controller/cmd/beads-viewer/templates/partials/`:

| Key        | Type       | What it exercises                        |
| ---------- | ---------- | ---------------------------------------- |
| `schedule` | `trigger`  | `/triggers` listing — cron + tz + enabled (was `type_schedule.html`; retired in gd-vK3RKOkRPW after Phase 3b/D10 removed `type=schedule`) |
| `agent`    | `agent`    | `type_agent.html` — roster fields        |
| `advice`   | `advice`   | `type_advice.html` — scope + body        |
| `decision` | `decision` | `type_decision.html` — options list      |
| `formula`  | `formula`  | `type_formula.html` — step list          |
| `mr`       | `mr`       | `type_mr.html` — pipeline + branches     |
| `generic`  | `task`     | `type_generic.html` — fallback render    |

The full spec — including required-field shapes — lives in
`seed/fixtures.mjs`. Adding a fixture is one entry there + a re-seed.

### Custom type config

`mr` is not in the daemon's built-in type registry (see
`kbeads/internal/server/config.go`). The seed script PUTs a `type:mr`
config on first run so `kd create --type=mr` is accepted. This is also
idempotent — re-runs detect the existing config and skip.

### Seed script

```sh
make seed-beads-viewer-e2e
```

What it does:

1. For each entry in `seed/fixtures.mjs:TYPE_CONFIGS`, ensure the type
   config exists on the daemon (`kd config get` → if missing,
   `kd config create`).
2. For each entry in `seed/fixtures.mjs:FIXTURES`, find a bead by its
   `fixture:e2e:<key>` label or create one. Capture the id.
3. Write `fixtures/ids.json` (`{ "<key>": "kd-...", ... }`) and
   `fixtures/manifest.json` (daemon URL + timestamp for debugging).

### How the seed runs in tests

`playwright.config.js` declares `globalSetup: './globalSetup.mjs'`,
which calls `seed.mjs` before the first test. Skip via
`BEADS_VIEWER_E2E_SKIP_SEED=1` for tight inner-loop dev when you have
already seeded in this shell.

The `tests/fixtures.spec.js` smoke spec asserts that the manifest
covers every canonical key and each fixture id resolves to a non-error
page on the viewer. Per-type assertions on the *content* of those pages
belong to later phases (T5/T6).

## OIDC sessions (gd-ZTu68qjfEC)

The default viewer runs dev-auth-bypass and writes to the daemon with the
harness fleet token (`e2e-fleet-token`, subject `e2e-admin`). kbeads refuses
that token for some writes a human makes:
answering a decision (`decision_resolver_authz.go`) and gardener budget and
counter fields (`autonomous_field_authz.go`). Specs that need a human principal
use the production path instead: a verified OIDC bearer.

`oidc-stub/server.mjs` stands in for Keycloak. It serves discovery and a JWKS
over HTTPS (beads-viewer requires an `https://` issuer) and writes its RS256
signing key and a CA bundle to `$OIDC_STUB_DIR`. `oidc-stub/mint.mjs` signs
Keycloak-shaped access tokens (`realm_access.roles`, `email_verified`) for any
email and roles. When `$OIDC_STUB_DIR/state.json` exists, `playwright.config.js`
boots a second viewer in OIDC mode on `BEADS_VIEWER_OIDC_PORT` (bypass off,
`BEADS_VIEWER_REQUIRE_USER_BEARER_WRITES=1`, `SSL_CERT_FILE` set to the stub's
bundle). A spec opts in per describe block:

```js
import { oidcSession, requireOIDCStub } from './_oidc.js';

test.describe('answering', () => {
  requireOIDCStub(test); // skips locally without a stub; never skips in CI
  test.use(oidcSession('someone@example.test', ['gardenio-operator']));
  // ...
});
```

The daemon must trust the stub too, so the stub has to be running before
`kd serve` starts. `e2e.yml`'s viewer job sets this up: it starts the stub and
then starts the phase-2 daemon with `BEADS_OIDC_ISSUER_URL`,
`BEADS_OIDC_AUDIENCE` and `SSL_CERT_FILE` taken from `state.json`. To do the
same locally:

```sh
node oidc-stub/server.mjs &   # writes oidc-stub/.state/state.json
S=oidc-stub/.state/state.json
BEADS_OIDC_ISSUER_URL=$(node -p "require('./$S').issuer") \
BEADS_OIDC_AUDIENCE=$(node -p "require('./$S').audience") \
SSL_CERT_FILE=$(node -p "require('./$S').caBundleFile") \
  kd serve   # plus your usual BEADS_DATABASE_URL etc.
```

A daemon reached via port-forward does not trust the stub, so without the
stub these specs skip locally.

### Writing as an agent

kbeads takes a write's author from the credential and honours no `X-Actor`
override (the shared static token that honoured one is retired,
gd-ke6PC7bRto). A spec that needs a comment authored by an agent (the Home
rail joins comments to agent cards by author) calls `mintAgentToken(agentId,
agentName)` from `tests/_oidc.js` and writes with `kd --token <token>`. It
registers a per-agent fleet token (`agent-<bead id>`, subject `<agent name>`)
the way the controller does in prod, as a token-mint machine principal: a
stub-signed service-account bearer for `TOKEN_MINT_CLIENT`
(`gardenio-e2e-token-mint`), which the daemon must list in
`BEADS_MACHINE_CLIENTS` (`e2e.yml` sets it for phase 2; add it to the local
`kd serve` above).

## htmx-idle wait pattern

htmx swaps are async. Tests must wait on the htmx in-flight counter, not
on arbitrary sleeps. Use the helper:

```js
import { waitForHtmxIdle } from './_helpers.js';

await page.locator('[hx-get]').click();
await waitForHtmxIdle(page);
await expect(page.locator('#swapped-target')).toContainText('expected');
```
