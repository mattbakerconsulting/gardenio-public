# Research: `git-blob` Bead Type — (repo, commit, path) → File Contents

**Status**: Research / plan-of-record (NOT implementation)
**Author**: thread-1777823322-836389
**Date**: 2026-05-03

## TL;DR

Today, when an agent opens a GitLab MR or pushes a branch, the *result* of that work — the changed files at a specific commit — has no first-class representation in the bead graph. The MR is shadow-tracked as `mr_*` fields on the issue bead, but the actual code is opaque to the constellation: no node, no edge, no embedding, no diff.

This research proposes a **new bead type, `git-blob`**, that captures one immutable triple: `(repo, commit_sha, path) → file contents`. Each registration is an idempotent, content-addressed snapshot of one file at one commit. Multiple `git-blob` beads bundle naturally under a parent issue/MR bead, so an agent's PR becomes a small subgraph of (issue → blobs) the operator can navigate, search, embed, and diff.

This is explicitly **a compromise**:
- We do not try to model the full git DAG (commits, trees, parents, branches, refs).
- We do not maintain a live mirror of any repo.
- We capture only the (commit, path) pairs an agent or operator chooses to register, when they choose to register them.

That compromise is the whole point: it gives us the smallest possible primitive that lets agent-produced code live in the bead graph without forcing kbeads to become a code-host.

This doc surfaces the design forks that need an operator decision before implementation lands. Implementation tasks are listed in [§ 11 Phased work breakdown](#11-phased-work-breakdown) and will be turned into a research epic alongside this doc; **none of those tasks are a green light to ship code** — each ends in an ADR or design artifact, and the operator authorizes a separate implementation epic only after the research lands.

The decisions surfaced as `gb decision` checkpoints are listed in [§ 10 Decision checkpoints](#10-decision-checkpoints).

## 1. Problem statement

### 1.1 What we have today

- Agents open MRs in GitLab; the gitlab-bridge populates `mr_url`, `mr_iid`, `mr_title`, `mr_state`, `mr_merged`, `mr_pipeline_status`, etc. as fields on the originating issue bead (see `mrFields` in `kbeads/internal/server/config.go:21`).
- The MR's *contents* — what code changed, in which files, at what commit — exist only in GitLab. Inside kbeads they are a URL string and a state enum.
- Typed mentions (research doc: `research-typed-mention-syntax.md`) let prose link `kd-` IDs to other `kd-` IDs, but there are no `kd-` IDs to point at for "this file at this commit."
- Embedding search (`design-embedding-search.md`) is wired for bead description/notes but cannot reach into file contents because file contents aren't beads.

### 1.2 Why that's a problem

When an operator (or another agent) is investigating a bead, they ask questions the current model can't answer:

| Question | Today | With `git-blob` |
|---|---|---|
| What did ka-X actually change? | Click out to GitLab. | Walk the bead graph: ka-X → blobs. |
| Find any work that touched `internal/server/config.go` last week. | grep MR list, click, eyeball diffs. | `kd list --type=git-blob -f path=internal/server/config.go --since=7d`. |
| Semantic search over recent agent-written code. | Not possible. | pgvector embedding over `git-blob.content`. |
| Show me the diff between this fix and the prior version of the same file. | git CLI in cloned repo. | Two blob beads + a diff endpoint. |
| Did the merged code match the plan in the parent epic? | Read MR, read epic, compare manually. | Edge: epic ←parent— task ←blocked-by— blob; render constellation. |

The cost of *not* having this is that the bead graph systematically under-represents agent work: the planning lives in beads, the code lives in git, and the only join is a URL string.

### 1.3 Why "snapshot" beats "live mirror"

A live git mirror — listening to push events, materializing every commit's tree as beads — is the obvious *complete* answer. It is also a much larger system: cross-fleet ref tracking, diff-storage cost, churn, cleanup, repo permissions, multi-tenant concerns. Matt's framing is that we don't need that. We need:

> "...a compromise that lets us relate git PRs generated by gardenio live in beads as part of the graph without being a pain."

The compromise is: agents (or operators, or the gitlab-bridge) opt-in by registering one (repo, commit, path) tuple at a time. Each tuple becomes one immutable bead. Volume is bounded by what we choose to register, not by repo activity.

### 1.4 Goals

1. New bead type `git-blob` with deterministic identity from `(repo, commit_sha, path)`.
2. Idempotent registration: re-registering the same triple returns the same bead.
3. File content stored or referenced safely (text, binary, large files, secrets).
4. Natural integration with typed mentions and the existing graph (parent, child, blocks, supersedes).
5. Discoverable via list filters (repo, commit, path, language, size) and embedding search (text content).
6. CLI ergonomics: agent-friendly registration in one command. No git clone required when a remote API can serve the blob.
7. Lifecycle clarity: when does a blob bead close? When is it GC'd?
8. Security: no accidental secret leaks; redaction or scan path before persisting.

### 1.5 Non-goals

- A complete git mirror (commits, trees, refs, branches, tags as beads).
- Cross-repo merge resolution.
- Bidirectional sync (changes to bead → git).
- Browsing / listing all files in a commit (only the registered ones).
- Version-control semantics (this is a snapshot store, not a VCS).
- Replacement for existing `mr_*` fields on issue beads — those keep tracking MR state; `git-blob` beads track *content* at a commit.

## 2. Design space — type schema

### 2.1 Required identity fields

Three fields uniquely identify a snapshot:

| Field | Type | Notes |
|---|---|---|
| `repo` | `string` | Canonical, normalized. Forms surveyed in [§ 3](#3-design-space--repo-identity). |
| `commit_sha` | `string` | Full 40-char lowercase hex. Reject short SHAs at the API. |
| `path` | `string` | POSIX path relative to repo root. No leading `/`. UTF-8 only. |

These three are required and immutable; they form the natural key. See [§ 4](#4-design-space--bead-identity-and-idempotence) for how they map to the `kd-` ID.

### 2.2 Content fields

| Field | Type | Notes |
|---|---|---|
| `blob_sha` | `string` | Git blob SHA-1 of the content. Computed on ingest, not supplied. Lets two `git-blob` beads with different `(repo, commit, path)` but identical content be detected as duplicates without re-reading content. |
| `file_size` | `integer` | Bytes. |
| `encoding` | `enum` | `text`, `base64` (binary), `truncated-text`, `truncated-base64`, `omitted`. Determines how to decode `content`. |
| `content` | `string` | The file body, encoded per `encoding`. Subject to size cap (§ 5). |
| `content_ref` | `string` | When content is offloaded (e.g. S3 URL or content-addressed store key). Mutually exclusive with `content`. |
| `language` | `string` | Auto-detected from path/extension on ingest. Optional override. |
| `mime_type` | `string` | Auto-detected. Optional. |
| `truncated` | `boolean` | True when content was capped at the size limit. |
| `secrets_redacted` | `boolean` | True when a secret-scanner found and stripped patterns; details go in `secrets_summary`. |
| `secrets_summary` | `json` | Redaction record: `[{rule:"aws-access-key", line:42, replacement:"<REDACTED>"}, ...]`. Never the original secret. |

### 2.3 Provenance / context fields

| Field | Type | Notes |
|---|---|---|
| `commit_message` | `string` | First line; full message goes in `notes`. Optional. |
| `commit_author` | `string` | `Name <email>`. Optional. |
| `commit_committer` | `string` | Optional. |
| `committed_at` | `timestamp` | Optional. |
| `branch` | `string` | Branch the commit was registered from, when known. *Not* part of identity. |
| `parent_commit_sha` | `string` | The first parent. Lets clients walk back without re-querying git. Optional. |
| `prior_blob_id` | `string` | When known (e.g. registered alongside the parent commit's snapshot of the same path), points at the previous `git-blob` bead for the same `(repo, path)`. Enables fast diff. |
| `gitlab_project_id` | `string` | When sourced from GitLab. |
| `gitlab_mr_iid` | `string` | When the snapshot was captured as part of an MR registration. |
| `source` | `enum` | `agent-cli`, `gitlab-bridge`, `manual`, `backfill`. |

### 2.4 Suggested write policy

```jsonc
"write_policy": {
  "project_scoped": true,    // restrict registration to authorized project
  "escalatable": true        // allow escalation when access denied
}
```

Open question (§ 10 D-2): should `git-blob` write require `min_role: gardenio-admin` to limit secret-leak blast radius? Default proposal is **no** — gate via project scope and a server-side secret scan, not by role.

## 3. Design space — repo identity

We need a single canonical `repo` string so two registrations of the same repo dedup correctly. Candidates:

| Form | Example | Pros | Cons |
|---|---|---|---|
| Full HTTPS clone URL | `https://gitlab.com/example-org/gardenio.git` | Already what users paste. | URLs vary (`http`/`https`, trailing `.git`, mirrors, vanity hosts). Need normalization. |
| Provider + path | `gitlab.com/example-org/gardenio` | Stable, host-prefixed. | Loses scheme; SSH-only repos awkward. |
| `<provider>:<project_id>` | `gitlab:12345` | Bulletproof against renames. | Opaque to humans. Requires a lookup. |
| Repo nickname (registered config bead) | `gardenio` | Pretty. | Adds a level of indirection per fleet. |

**Recommended default:** store *both* a normalized `repo` (provider+path, e.g. `gitlab.com/example-org/gardenio`) and a `repo_id` (provider:numeric_id when known) so we get both stable identity and human readability. Strip `.git` and scheme on ingest.

Surfaces as decision **D-1** (§ 10).

## 4. Design space — bead identity and idempotence

Three options for how the `kd-` ID relates to `(repo, commit_sha, path)`:

### 4.1 Standard random `kd-` ID + uniqueness index (recommended)

- Bead ID is a normal nanoid (`ka-0000001713`).
- A new uniqueness constraint over `(type='git-blob', repo, commit_sha, path)` enforces dedup.
- Registration upserts: if the triple already has a bead, return it; otherwise create.
- **Pros:** uses existing ID infrastructure; predictable URLs; survives schema changes to the triple format.
- **Cons:** the ID itself is opaque — operators have to look up the bead to see the triple.

### 4.2 Deterministic ID derived from triple hash

- ID = `kd-<base32(hash(repo + commit_sha + path))[:10]>`.
- **Pros:** content-addressed; same triple → same ID across fleets without coordination; no DB lookup needed to dedup.
- **Cons:** breaks the ID-format invariant (random nanoid); collisions possible at 10 chars (50-bit) under heavy registration load. Migration painful if hash changes.

### 4.3 Slug-based

- ID is random; a slug like `git-blob/gitlab.com/example-org/.../config.go@deadbeef` is set on the bead.
- **Pros:** human-friendly references in prose; works with existing mention extractor.
- **Cons:** slugs aren't unique-by-default; long; collide with other slug uses.

**Recommended default: 4.1.** It re-uses the existing ID generator and adds one DB constraint; the `(repo, commit, path)` triple is queryable via list filters. Surfaces as decision **D-3** (§ 10).

## 5. Design space — storage strategy

File contents could be small (a 200-byte YAML) or large (a 5MB generated SQL dump). Storing 5MB inline in the `fields` JSONB column is feasible but ugly: it loads the full content on every bead read, blows up event payloads, and balloons the audit log.

### 5.1 Tiered storage proposal

| Size | Storage | Notes |
|---|---|---|
| ≤ 64 KB | Inline in `fields.content` | Default for source files. |
| 64 KB – 1 MB | New `git_blob_content` table, content-addressed by `blob_sha`. | One row per unique blob; many `git-blob` beads point at the same row when content is identical. |
| > 1 MB | Object store (S3/MinIO), `content_ref = s3://...`. | URL stored in bead; presigned for read. |
| > 16 MB (configurable) | Reject with 413 OR store metadata only, `encoding=omitted`. | Don't accept arbitrary binaries. |
| Binary (per content sniff) | `encoding=base64`, same tiering. | Embeddings disabled; UI displays metadata only. |

The `git_blob_content` table is content-addressed (`blob_sha PRIMARY KEY`), refcounted by `git-blob` beads. Storing content separately from the bead is precedented by `bead_embeddings` (migration 005).

**Cost note:** 1KB average file × 100 registrations/day × 365 days ≈ 36MB/year inline — comfortable for JSONB. The tiering matters at the long tail (build outputs, generated YAML).

Surfaces as decision **D-4** (§ 10).

### 5.2 Why content-address even small inline blobs

Two `git-blob` beads with the same `blob_sha` (e.g., the same file unchanged across two commits) should share the same physical content row when stored externally. For inline storage we duplicate, accepting the cost in exchange for query simplicity.

## 6. Design space — references and graph integration

### 6.1 How issues / MRs link to blobs

Three approaches, can combine:

1. **Typed mention from issue → blob.** The agent writes `produces(ka-blob1)` in the issue description (or a comment). The reference extractor records the edge.
2. **Explicit dep.** `kd dep add ka-issue ka-blob --type=parent-child` — the issue is the parent, blob is the child. Reuses existing dep machinery.
3. **`origin_bead` field on the blob.** The blob bead carries `origin_bead = ka-issue`; we render that as a back-edge.

**Recommended default:** all three, but in a layered way:
- The blob carries `origin_bead` for canonical attribution (1:1, set on registration).
- The graph edge materializes as a typed-mention or dep when the operator wants to wire the blob to additional contexts (e.g., a related epic, a superseding fix).
- Typed mention verbs to consider extending: `produces` (issue→blob), `produced-by` (blob→issue), `derives-from` (blob→prior-blob).

### 6.2 New typed-mention verbs

The typed-mention research (`research-typed-mention-syntax.md`) defines a closed verb set. Adding `produces`/`produced-by` and `derives-from`/`derived-from` is in scope of *that* research, not this one — flag the dependency in the typed-mention epic.

### 6.3 What renders in beads-viewer

A `git-blob` bead in the constellation should:
- Display compact (path + short SHA), not the full content.
- Be clickable to a blob detail panel.
- Render dashed edges from blob → origin_bead (typed mentions) and solid edges for explicit deps.
- Be filterable out by default (constellation gets noisy fast).

## 7. Design space — ingestion

### 7.1 CLI surface

Sketch:
```sh
kd git-blob add \
  --repo gitlab.com/example-org/gardenio \
  --commit deadbeef0123... \
  --path internal/server/config.go \
  [--from-file path/on/disk]                 # local content; else fetched
  [--source gitlab|github|local]             # provider hint
  [--origin-bead ka-X]                       # bead this blob derives from
  [--mr ka-0000004786]                       # link to MR/issue
  [--branch feat/xyz]                        # context
  [--no-redact]                              # disable secret scan (admin)
```

Fetch strategies:
- **Local clone:** if `cwd` is a clone of the repo, read directly.
- **GitLab API:** `GET /projects/{id}/repository/files/{path}/raw?ref={sha}` — no clone needed.
- **GitHub API:** `GET /repos/{owner}/{repo}/contents/{path}?ref={sha}` (≤1MB) or git data API (larger).
- **Provided file:** `--from-file` for offline registration.

Output: bead ID + dedup status (`created` vs `existing`).

### 7.2 Bridge integration

The gitlab-bridge already touches MR state on issue beads. Optional, deferred follow-up: when an MR merges, the bridge could batch-register `git-blob` beads for the changed files at the merge commit, link them under the issue. **Out of scope for the initial epic** — it's infrastructure work that depends on the rest of the design landing first.

### 7.3 Idempotence and concurrency

`kd git-blob add` is upsert. Two concurrent registrations of the same triple should produce one bead, not two. Implementation note: the uniqueness index must be checked inside the same transaction that creates the bead; on conflict, return the existing row.

## 8. Design space — security

### 8.1 Secrets

Source files routinely contain false-positive secret-shaped strings (test fixtures, examples). We should run a server-side scanner on every registration:

- Default scanner: gitleaks (already in repo per `.gitleaks.toml`).
- Behavior on hit: redact the matched span, set `secrets_redacted=true`, populate `secrets_summary`. Refuse to store the unredacted version.
- Override: `--no-redact` flag requires `min_role: gardenio-admin`. Audit log records the override.

### 8.2 Access control

- `project_scoped: true` write policy: only operators authorized for the project label can register blobs targeting that project.
- Read policy: same as any bead — fleet-bounded, project-scoped if labels apply.
- A `git-blob` for a private repo should not become world-readable by virtue of being a bead. Clarify the inherited fleet-isolation guarantees.

### 8.3 PII / license / size DoS

- Maximum size cap (configurable, default 16MB) prevents one registration from blowing up storage.
- Per-fleet rate limit on `git-blob` creation prevents enumeration attacks.
- License-text files (LICENSE, NOTICE) are fine; PII is the operator's responsibility to redact before registering.

## 9. Design space — lifecycle

### 9.1 Status transitions

`git-blob` beads are immutable historical records. Default:
- Status `open` on creation. Stays `open` indefinitely.
- Closing is allowed but discouraged: only when the underlying repo or MR is hard-deleted upstream and the operator wants the blob hidden from default views.
- No `in_progress` semantics (it's data, not work).

Alternative: introduce `kind: data` for `git-blob` (instead of `issue`) so it doesn't pollute the work-tracking views. **Recommended.** Surfaces as decision **D-5** (§ 10).

### 9.2 GC

- An "orphan" `git-blob` is one with no incoming references (no typed mentions, no deps, no `origin_bead`).
- After 90 days an orphan is eligible for soft-delete (existing migration 009 supports this).
- Refcounting in `git_blob_content` cleans up content rows when the last referencing blob bead is hard-deleted.

### 9.3 Repo deletion

When a repo is removed from the fleet's allowed-projects, existing blobs for that repo:
- Stay readable (historical record).
- Are excluded from default list filters.
- Are not registerable (new writes fail).

## 12. Risks and unknowns

- **Volume blow-up.** If agents enthusiastically register every file in every MR, blob count grows fast. Mitigations: opt-in per repo, per-fleet rate limit, GC, embedding opt-in.
- **Secret leaks.** Already mitigated by scanner; remaining residual risk in unusual encodings (encrypted blobs, custom encodings). Consider a post-hoc scan job to retro-redact.
- **Path normalization.** Symlinks, case-sensitivity (`Foo.go` vs `foo.go`), Windows-style paths in cross-platform repos. Pick POSIX, reject the rest at the API.
- **Repo renames.** A repo renamed upstream invalidates the canonical `repo` field. Mitigations: store `repo_id`; provide an admin-only migration tool.
- **Fleet scoping.** A blob bead's repo may be readable by multiple fleets. Default to fleet-isolation; cross-fleet sharing is out of scope.
- **Diff tooling drift.** A "diff between two blob beads" feature is tempting but not in scope here. Note for follow-up.
- **Coordination with typed-mention research.** P5 lands edges that depend on verb extensions which live in `research-typed-mention-syntax.md`. The two epics must coordinate; default plan is to ship typed mentions first and layer the verbs in P5.

## 13. Out of scope

- Live mirroring of any repo.
- Full git DAG (commits, trees, refs) as beads.
- Bidirectional sync.
- Code-aware indexing (AST, symbols, callgraph). Could be a future skill on top, not a primitive in kbeads.
- Rich diff UI inside beads-viewer beyond a simple side-by-side. Note for follow-up.
- Webhook-driven auto-registration. The bridge follow-up in P8 is opt-in; webhook event firehose is a separate decision.
